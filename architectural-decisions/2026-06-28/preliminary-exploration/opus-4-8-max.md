## Schema/column adjustments, ranked by cost-of-delay

**1. The chunk has no `tsvector` + GIN — this is the big one.** Your stated goal is "semantic + exact match both accepted just like the user store." The user store's exact-match lane works only because `UserStoreDocChunk` carries `contentTsv Unsupported("tsvector")` plus a trigger (`trg_user_store_chunk_tsv`, migration `20260311035622`) and a GIN index. `ConversationMemoryChunk` has neither, so right now there's no fulltext lane to hybridize against — `searchConversationMemory.sql` and `searchMemoryByConversation.sql` are pure cosine. Add the column + GIN + trigger now, because backfilling a tsvector across a populated table (with the null-byte sanitization dance your `backfill-tsvector.ts` already handles) is the exact pain you avoid by doing it on an empty table.

One nuance the user store doesn't face: your source text is `transcriptMarkdown`, which is wrapped in `<model provider="anthropic" name="...">` tags. A naive `to_tsvector('english', "transcriptMarkdown")` indexes *model, provider, anthropic, name, claude, opus* into every single chunk and poisons both `ts_rank_cd` and your Jaccard overlap. Strip the wrappers in the trigger:

```sql
NEW."transcriptTsv" := to_tsvector('english',
  regexp_replace(COALESCE(NEW."transcriptMarkdown", ''), '</?model[^>]*>', ' ', 'gi'));
```

And since the per-chunk `summary` lands *after* insert (async), this is also your chance to make the tsv a weighted composite — `setweight(to_tsvector(summary), 'A') || setweight(to_tsvector(transcript), 'B')` — so a keyword hit in the model-written summary outranks an incidental hit in the raw transcript. That means the trigger fires on `BEFORE INSERT OR UPDATE OF "transcriptMarkdown", summary`. Worth it; it's the difference between "exact match" being a toy and being good.

**2. Store ordinals on the chunk.** Your entire mental model is 0-based ordinals, but the chunk only persists `messageIdStart`/`messageIdEnd` (cuids) and the two timestamps. To answer "what's already chunked," "is there a gap," or "give me the chunk covering ordinal 40" you currently have to join back to `Message`. Add `ordinalStart Int` and `ordinalEnd Int` to the chunk. Then the watermark query for the worker becomes trivial, contiguity/gap detection is arithmetic, and your `provenanceId` can drop the long cuid pair in favor of `${conversationId}-${ordinalStart}-${ordinalEnd}-${chunkIndex}` (compact, debuggable, still unique).

Relatedly, `ConversationMemoryContext.lastChunkedMessageIndex Int?` is ambiguously named — is it an ordinal or a count? If it's meant as the high-water ordinal, rename it `lastChunkedOrdinal` so the worker's intent (`WHERE ordinal > context.lastChunkedOrdinal`) is self-evident. You technically don't even need it — `MAX(ordinal) WHERE conversationMemoryChunkId IS NOT NULL` derives it — but the watermark is cheaper than the aggregate on every tick.

**3. Filter the memory search by `embeddingModel`, and flip the defaults to context-4.** `searchUserStoreChunksHybrid.sql` filters `WHERE chunk."embeddingModel" = $7`; neither memory search file does. context-3 and context-4 embeddings are not in the same vector space, so the instant you bump and any context-3 rows survive, your HNSW results are garbage cosine. The table's empty today, so this is a one-line `AND mc."embeddingModel" = $n` insurance policy that costs nothing now and saves a re-index later. While you're there, the schema still defaults `ConversationMemoryStore.embeddingModel` and `ConversationMemoryChunk.embeddingModel` to `"voyage-context-3"` even though `embedChunksContextual` already defaults to `"voyage-context-4"` — align them.

**4. Add an idempotency constraint mirroring the user store.** The chunk's only uniqueness is `@unique` on `provenanceId`. `UserStoreDocChunk` additionally carries `@@unique([docId, chunkIndex, schemaVersion])`. Add `@@unique([conversationId, chunkIndex, schemaVersion])` (and arguably `@@unique([conversationId, ordinalStart, schemaVersion])` so no two chunks ever claim the same starting ordinal). This makes re-runs and schema-version migrations safe independent of how you compute `provenanceId`.

**5. Decide the "summary in history" representation now — it gates a `MessageType`.** "Leaving the summary in conversation history" has two readings, and they diverge at the schema:

- If summaries are *materialized as `Message` rows* (so they're real history, persisted, queryable as messages), they consume ordinals and — critically — become eligible for re-chunking, i.e. recursive summarization of summaries. You'd need to exclude them, which means adding `MEMORY_SUMMARY` to the `MessageType` enum (or an `isMemorySummary Boolean`) so every chunking query can do `WHERE messageType != 'MEMORY_SUMMARY'`. Adding an enum member is free now and a data migration later.
- If summaries stay on the chunk (`ConversationMemoryChunk.summary` already exists) and are *substituted into the prompt at assembly time* — replacing the raw oldest slice with `summary` + the ordinal range while keeping the live window bounded — then no new rows, no ordinal pollution, fully reversible, and `Message.conversationMemoryChunkId` is exactly the pointer you need.

I'd go with the second: it's the classic context-compaction pattern, it matches the fields you already have (`summary`, `rollingSummary`, `conversationMemoryChunkId`), and it keeps the ordinal sequence pristine. But if you genuinely want summaries to be first-class, durable history items the user can scroll to, add `MEMORY_SUMMARY` before anything writes to `Message`.

**6. Minor: `MemoryChunkBoundaryReason` has no count trigger.** You describe the trigger as "every n messages," but the enum is `TOKEN_LIMIT | IDLE_TIME | TOPIC_SHIFT | SESSION_END | OTHER`. Add `MESSAGE_COUNT` (or `WINDOW_FULL`) so the boundary reason on count-driven flushes isn't lying as `OTHER`.

## The one genuinely architectural fork: context-4 granularity

This is the decision I'd make consciously rather than discover later, because it sets chunk row granularity. context-4's whole edge over a flat embedding model is that `embedChunksContextual` takes `inputs: readonly (readonly string[])[]` and returns one *contextualized* embedding per inner-array element — each chunk's vector is conditioned on its neighbors in the same inner array. But `ConversationMemoryChunk` has a single `embedding` and a *range* (`messageIdStart`→`End`). So:

- **Section-granular (recommended for v1):** one chunk row = one section = one embedding of the concatenated section transcript (`inputs = [[sectionTranscript]]`). Matches your range fields and your "one summary per section" exactly. You can batch multiple sections per request for throughput, but note that distinct inner arrays don't share context, so batching `[[s0],[s1],[s2]]` gives byte-identical vectors to embedding them one at a time — it's purely a round-trip optimization. Ship this.
- **Message-granular:** one chunk row = one message, embedded as an element of the section's inner array (`inputs = [[msg0, msg1, …, msgK]]`) so each message vector carries section context, with `ordinalStart == ordinalEnd`. This is where context-4 actually earns its name and where retrieval recall on "which exact message said X" jumps — but it multiplies rows and breaks the clean one-summary-per-section unless you promote the section to its own tier above the chunk.

Given that you described slices of *messages* and one summary per *section*, section-granular fits your intent and the schema as-is. File two enhancements for later: (a) message-granular retrieval if recall disappoints, and (b) a sliding-window trick — embed adjacent sections in one inner array so each section vector is informed by its neighbors — with the caveat that it complicates idempotency (re-embedding one section perturbs its neighbors').
